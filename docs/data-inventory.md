# PubAZ 데이터 구분: 회원 이후 서버가 관리할 것 / 아닌 것

> 상태: **설계 1단계 (회원 시스템)**, 2026-11-05. 비용(DB 용량, 요금)은 아직 정하지 않았다. 10장에 나중에 비용을 정할 때 볼 것만 모아 둔다.
> 서버 전체 구조는 [`server-design.md`](server-design.md)에 있다. 이 문서의 결정이 그 문서와 다르면 이 문서가 우선한다(11장).
> 법 조항과 보관 기간은 설계 메모다. "법무 확인"이 붙은 것은 처리방침을 쓰기 전에 전문가 확인을 받는다.

## 1. 1단계 결정 기록

| 항목 | 결정 | 메모 |
|---|---|---|
| 가입 시점 | **익명으로 시작** | 설치하면 바로 쓴다. 기록 백업, 기기 이동, Pro 결제, AI 추가 횟수가 필요할 때 가입을 권한다 |
| 로그인 수단 | **카카오, 애플, 구글, 이메일 인증코드** | 이메일은 비밀번호 없이 일회용 코드로 한다 |
| 인증 방식 | **관리형 Supabase** (Auth + Postgres) | 익명 로그인과 위 네 가지 로그인을 Supabase가 처리한다. 우리가 만든 HMAC 토큰은 Supabase 토큰 검증으로 바뀐다(11장) |
| 나이 | **앱 사용은 나이 확인 없음. 가입과 실시간 AI 대화는 만 19세 이상 (잠정)** | 아래 참고 |

**나이 정책 메모.** 비교 대상인 GTO Poker Trainer(Peka Software)는 앱 등급이 4+이고 앱 사용에는 연령 제한이 없다. 18세 확인은 AI에 직접 질문하는 "Ask Nash"를 처음 쓸 때만 받는다. PubAZ도 익명 시작을 골랐기 때문에 같은 구조가 된다.

- 퀴즈, 차트, 계산기, 기록 화면, 미리 만든 해설(D): 누구나, 나이 확인 없이 쓴다.
- 가입, 그리고 사용자가 직접 질문하는 실시간 AI 대화: 처음 쓸 때 만 19세 이상인지 확인한다.
- 확인 방법(본인 선언 / 본인인증)은 아직 정하지 않았다. 본인 선언이면 기록에는 "만 19세 이상이라고 답함"으로 남긴다. "확인됨"이라고 쓰지 않는다.
- 앱 사용 자체를 19세로 막을지는 스토어 등급을 정할 때 다시 본다.

## 2. 분류 기준

모든 데이터를 아래 다섯 칸 중 하나에 넣는다. "관리한다"는 서버가 저장하고, 백업하고, 정한 때에 지우고, 개인정보처리방침에 적는다는 뜻이다. **"보낸다"와 "저장한다"는 다르다.** 서버를 지나가기만 하는 데이터도 처리방침에는 적어야 한다(5장, 6장).

| 분류 | 원본 | 서버가 하는 일 | 관리 부담 |
|---|---|---|---|
| **A. 회원 데이터** | 서버 | 저장, 권한 판단, 정한 때 파기 | 있음 (개인정보 포함) |
| **B. 동기화 데이터** | 기기 | 로그인한 사용자의 복사본 보관, 다른 기기로 전달 | 있음 (용량이 가장 큼) |
| **C. 기기 전용 데이터** | 기기 | **저장하지 않는다.** 단 AI 대화 내역, 해설 노트, 접속 비밀번호는 요청할 때 중계 서버를 지나가고, 대화 내역과 해설 노트는 Anthropic까지 간다(5장) | 작음 |
| **D. 배포 콘텐츠** | 우리(운영자) | 누구에게나 같은 파일을 내려줌 | 버전 관리만 (개인정보 없음) |
| **E. 익명 집계** | 서버 | 사용자 id 없이 숫자만 보관. 동의한 사용자의 데이터로만 만든다 | 작음 (나중 단계) |

판단 순서:
1. 우리가 만든, 누구에게나 같은 것이면 **D**다.
2. 비밀값이거나 우리 서버에 남으면 안 되는 것(API 키, 대화 내역)이면 **C**다.
3. 권한, 돈, 한도, 법적 기록, 로그인 정보처럼 서버가 정답을 가져야 하는 것이면 **A**다. 기기 값은 믿지 않는다.
4. 사용자의 공부 기록이고 기기를 바꿔도 따라와야 하는 것이면 **B**다.
5. 사용자와 연결이 끊긴 숫자면 **E**다. 사용자 id에 묶인 값(예: 사용자 레이팅)은 E가 아니다.
6. 나머지(화면 상태, 다시 만들 수 있는 것)는 **C**다.

## 3. 전체 표

### A. 회원 데이터 (서버가 원본)

| 데이터 | 지금 | 회원 이후 위치 | 개인정보 | 지울 때 | 보존 |
|---|---|---|---|---|---|
| 사용자 id, 가입일, 탈퇴 상태 | 없음 (설계: `users`) | Supabase `auth.users` + 우리 `profiles` | 낮음 | 8장 | 계정 유지 동안 |
| 로그인 연결 (카카오·애플·구글·이메일) | 없음 (설계: `auth_identities`) | Supabase `auth.identities` | 중간 (공급자 id) | 8장 | 계정 유지 동안 |
| 이메일 주소 | 없음 | Supabase `auth.users.email` | **높음** | 8장 | 계정 유지 동안. 이메일 로그인에는 필요하다. 소셜 로그인에서는 공급자 동의항목에서 이메일을 빼는 것을 검토한다 |
| **소셜 로그인 프로필** (공급자가 준 닉네임, 이름, 프로필 사진 URL, 이메일) | 없음 | Supabase `auth.identities.identity_data`, `auth.users.raw_user_meta_data`. **Supabase가 자동으로 저장한다** | **높음** (실명일 수 있다) | 8장 | 카카오·구글 동의항목과 scope를 최소로 잡는다(Supabase의 카카오 안내는 닉네임·프로필 사진 동의항목을 설정하게 한다). 가입 직후 서버 함수로 이름·사진 필드를 지운다. 지우지 못하는 항목은 처리방침 수집 항목에 적는다 |
| **로그인 세션·인증 감사 로그** | 없음 | Supabase `auth.sessions`(IP 포함), refresh token, 인증 감사 로그 | 중간 (IP) | 세션은 로그아웃·만료 때 지워진다 | 감사 로그 보관 기간은 Supabase 설정을 확인한 뒤 정한다 |
| 연령 확인 기록 | 없음 | `profiles.age_verified_at`, `age_method`(본인 선언 / 본인인증) | 낮음 | 8장 | 계정 유지 동안. **생년월일은 저장하지 않는다** |
| 약관·개인정보처리방침 동의 | 없음 | `consents(user_id, doc, version, agreed_at)` | 낮음 | 8장의 예외 (분쟁 대비 기간 분리 보관, 법무 확인) | 계정 유지 동안 |
| 마케팅 수신 동의 (선택) | 없음 | `consents` (동의 시각, 채널: 푸시/이메일, 야간 수신 동의 여부) | 낮음 | 8장 | 철회 즉시 반영. 광고성 정보를 보내면 정보통신망법상 2년마다 수신 동의 여부를 알리고, 오후 9시~오전 8시 전송은 따로 동의받는다(법무 확인) |
| 통계 집계 동의 (선택) | 없음 | `consents` | 낮음 | 8장 | 철회하면 다음 집계부터 뺀다(E) |
| 요금제·권한 (Pro, 만료일) | 없음 (설계: `entitlements`) | `entitlements` | 낮음 | 8장 | 계정 유지 동안 |
| 결제 기록 참조 | 없음 | `payments(user_id, provider, external_id, amount, at)`. 카드 정보는 결제사가 보관하고 우리는 받지 않는다 | 중간 | 8장의 예외 (법정 보존 기간 동안 분리 보관) | 전자상거래법상 계약·결제 기록 5년 (법무 확인) |
| AI 사용량 카운터 | 없음 (설계: `usage_counters`) | `usage_counters` | 낮음 | 8장 | 주간 기준이라 최근 6주만 남기고 지운다 ([free-plan.md](free-plan.md) 9장) |
| 기기 목록 | 기기 id는 `pubaz.device` (4장 참고) | `devices(device_id, user_id, platform, last_seen_at)` | 낮음 | 8장 | 계정 유지 동안. 90일 안 쓴 기기는 정리 |
| 사용자 레이팅 (오늘의 문제, 본인에게만 표시) | 없음 | `ratings(user_id, rating, rd, updated_at)` | 낮음 | 8장 | 계정 유지 동안. 사용자에 묶인 값이라 E가 아니다 |
| 운영 로그 (**모든 이용자, 익명 포함**) | **지금도 있다**: Vercel 함수 로그(`api/anthropic.ts` AI 중계 요청) | Vercel 런타임 로그, Supabase 로그 | 중간 (IP) | 탈퇴와 관계없이 보관 기간이 지나면 지워진다 | 요금제에 따라 짧다(Vercel 문서 기준 1시간~30일). 통신비밀보호법의 "3개월 이상" 보관 의무가 우리에게 적용되는지 법무 확인한다. 적용되면 기본 보관으로는 부족하므로 로그 전송(drain)으로 별도 저장소에 보관하고, 그 저장소도 6장 표에 넣는다 |

### B. 동기화 데이터 (기기가 원본, 로그인한 사용자만 서버에 복사본)

| 데이터 | 지금 위치 | 서버 | 개인정보 | 탈퇴 시 | 메모 |
|---|---|---|---|---|---|
| **퀴즈 기록 (`Attempt`)** | localStorage `pubaz.attempts.v1` | `attempts` (설계 완료, 코드 있음) | 낮음 (공부 기록). 단 각 기록에 기기 id가 들어 있다(4장) | 서버 복사본 파기, 기기 기록은 남음 | 용량의 대부분을 차지한다(10장). 추가만 하므로 충돌이 없다 |
| 이전 합계 (기록 기능 이전에 푼 문제) | **저장된 값이 아니다.** 아래 메모 | `legacy_tallies(user_id, payload)` 한 번만 업로드 | 낮음 | 파기 | 아래 메모 |
| 학습 설정: 차트 세트, AI 모델 선택, 해설 깊이 | localStorage `mygto.settings` (`chartSet`, `model`, `effort`) | `profiles.prefs` (작은 JSON) | 없음 | 파기 | 기기를 바꿔도 같은 환경이 되게. 마지막에 바꾼 값이 이긴다 |
| 나만의 해설 노트 | localStorage `mygto.settings.userNotes` | `profiles.notes` (**선택**: 사용자가 켜야 서버에 저장) | 중간 (자유 텍스트라 무엇이든 쓸 수 있다) | 파기 | "선택"은 **서버 저장**에만 해당한다. AI 코치를 쓰면 노트는 동기화 여부와 관계없이 매 요청 시스템 프롬프트에 들어가 Anthropic으로 간다(5장) |
| 핸드 기록 (펍 필드 통계용, 나중) | 없음 | 기능을 만들 때 정한다 | 정할 때 판단 | 파기 | 사용자가 켜는 동기화로만 받는다. 동의 문구는 그때 정한다 |

**이전 합계 메모.** `mygto.stats`는 기록 기능 이전 값이 아니라 **지금도 답할 때마다 늘어나는 누적 합계**다(`recordQuiz` → `recordAnswer`). 기록 화면의 "이전 기록"은 `legacyTotals()`가 상위 키 6개에 대해 "합계 − 기록 수"를 그때그때 계산한 값이다. 그래서:
- 서버에는 `mygto.stats`를 그대로 올리지 않는다. 그대로 올리면 기록과 이중으로 센다.
- 첫 동기화 때, 다른 기기의 기록을 pull·가져오기로 합치기 **전에** 이 차이값을 한 번 계산해 고정하고 그 값만 올린다. 합친 뒤에는 차이값이 틀어진다(기록이 늘면 0으로 떨어지고, 5,000건 상한으로 오래된 기록이 지워지면 커진다).
- 이전의 최고 연속 정답(`bestStreak`)과 하위 키별 합계(예: `preflop:<시나리오>`)는 기록에서 다시 만들 수 없다. 올리지 않으면 새 기기에서는 사라진다.

### C. 기기 전용 데이터 (서버에 저장하지 않음)

| 데이터 | 지금 위치 | 서버를 지나가나 | 이유 |
|---|---|---|---|
| 내 Claude API 키 | `mygto.settings.apiKey` | 아니다. 기기에서 Anthropic으로 바로 간다 | 비밀값이다. 서비스 단계에서는 이 방식 자체를 "개발자 모드"로 숨긴다 |
| 접속 비밀번호 | `mygto.settings.passcode` | **그렇다.** 비밀번호를 넣어 두면 AI 요청마다 `x-app-passcode` 헤더로 중계 서버에 가서 비교만 한다 | 지금 Vercel 중계용 임시 수단이다. 회원 시스템이 생기면 없앤다 (`keyMode`도 함께) |
| AI 코치 대화 내역 | localStorage `mygto.coach`. 스팟 하나당 대화 하나, 대화는 최근 40개까지(한 대화 안의 메시지 수는 제한 없음). 각 대화에 스팟 정보(`facts`), Anthropic에 보낸 그대로의 기록(생각 블록 포함), 화면용 텍스트, 마지막 수정 시각이 들어 있다 | **그렇다.** 질문할 때마다 그 대화 전체가 중계 서버를 지나 Anthropic(미국)으로 간다 | 개인정보가 섞이기 쉽고 데이터 중 가장 크다. 우리 서버는 **중계만 하고 저장하지 않는다**(Peka도 같은 방식). 기기 간 이동이 꼭 필요해지면 나중에 사용자가 켜는 옵션으로만 연다 |
| 동기화 상태 | `pubaz.attempts.v1` 각 행의 `syncedAt`·`rejected`, (예정) 마지막 pull 커서와 "기록 동기화" 스위치 | 아니다. 업로드·내보내기 전에 빠진다(`toPlain`) | 이 기기의 진행 상태다. 커서와 스위치는 학습 설정이 아니라 기기 전용 키에 둔다 |
| 로그인 세션 토큰 사본 | (예정) Supabase SDK가 기기에 보관 | 요청마다 보낸다 | 기기의 사본은 기기 전용이다. 서버 쪽 세션 기록은 A의 "로그인 세션"이다 |
| 기기 비밀값 (예정) | 아직 없음 (server-design 5.3) | 인증 때만 | Supabase 익명 로그인을 쓰면 Supabase 세션이 이 역할을 대신하므로 필요 없어질 수 있다(11장) |
| 화면 상태 (필터, 고른 탭, 진행 중인 핸드) | React 메모리 | 아니다 | 다시 만들 수 있다 |
| 기록 내보내기 파일 | 사용자가 받은 JSON | 아니다 | 사용자 소유다. 기록마다 기기 id가 들어 있으므로 공유하지 말라고 안내한다 |

### D. 배포 콘텐츠 (누구에게나 같음, 개인정보 없음)

| 데이터 | 지금 | 회원 이후 |
|---|---|---|
| 프리플랍 차트 세트 | 앱 코드 안 (`src/data/sets/*.ts`) | 앱 코드 또는 콘텐츠 팩. 버전을 붙여 "어느 차트 기준 채점인지" 남길 수 있게 한다 |
| 솔버 콘텐츠 팩 (포스트플랍) | 없음 | 정적 파일 + 매니페스트 (server-design 9장) |
| 오늘의 문제 문제 풀 | 없음 | 정적 파일 (server-design 10장) |
| 미리 만든 AI 해설 | 없음 | 정적 파일. 같은 스팟이면 모든 사용자에게 같은 해설을 주므로 사용자별 AI 비용이 들지 않는다. 나이 확인 없이 누구나 본다 |
| AI 코치 해설집 | 앱 코드 안 (`src/features/coach/knowledge.md`) | 서버가 프롬프트를 소유하는 단계에서 서버로 옮긴다 |

### E. 익명 집계 (나중 단계)

| 데이터 | 만드는 곳 | 원칙 |
|---|---|---|
| 문제별 난이도·정답률 (문제 레이팅) | 서버가 **집계에 동의한 사용자**의 `attempts`(오늘의 문제)에서 집계 | 결과는 사용자 id 없이 숫자만 저장한다. 동의는 설정에서 따로 받고, 철회하면 다음 집계부터 뺀다. 동기화 목적으로 받은 기록을 동의 없이 통계에 쓰지 않는다 |
| 펍 필드 통계 (사람들이 실제로 어떻게 치나) | 동의한 사용자의 핸드 기록(B)에서 집계 | 한 묶음에 사용자가 20명 미만이면 공개하지 않는다(server-design 11장과 같은 기준). 실존 인물 닉네임 단위의 기록은 만들지 않는다 |

## 4. 기기 저장소 정리 (localStorage 키별)

| 키 | 내용 | 분류 |
|---|---|---|
| `pubaz.attempts.v1` | 퀴즈 기록, 각 행의 동기화 상태 | 기록 = B, `syncedAt`·`rejected` = C |
| `pubaz.device` | 기기 id | 값은 기기에서 만들지만 기기에만 있지 않다(아래) |
| `mygto.stats` | 누적 정답률 합계, 연속 정답 | 기기 전용 계산값. 서버에는 "이전 합계" 차이값만 한 번 올린다(3장 B) |
| `mygto.settings` | 키 방식, 비밀번호, API 키, 모델, 해설 깊이, 해설 노트, 차트 세트 | **필드마다 다르다**: `apiKey`·`passcode`·`keyMode` = C, `model`·`effort`·`chartSet` = B, `userNotes` = B(선택) |
| `mygto.coach` | AI 대화 내역 | C (단 질문할 때마다 Anthropic으로 전송된다) |

**기기 id.** `pubaz.device` 값은 모든 `Attempt.deviceId`에 복사된다. 그래서 기록(`pubaz.attempts.v1`), 내보내기 파일, 서버 `attempts.device_id`·`payload`, 같은 계정의 다른 기기(pull)로 퍼진다. 가져오기한 기록은 원래 기기의 id를 그대로 갖는다. 지금 서버 뼈대(server-design 5.1)에서는 기기 id 하나로 익명 토큰을 받을 수 있으므로, Supabase 익명 로그인으로 바꾸기 전까지는 비밀값처럼 다룬다.

회원 시스템을 붙일 때 `mygto.settings`를 둘로 나눈다. 비밀값(C)은 기기 전용 키로, 학습 설정(B)은 동기화용 키로 옮긴다. 한 키에 섞여 있으면 실수로 비밀값까지 올릴 수 있기 때문이다.

## 5. 기기 밖으로 나가는 데이터

### 5.1 지금 AI 코치가 보내는 것 (이미 운영 중)

AI 코치에 질문할 때마다 요청에 다음이 들어간다.
1. 시스템 프롬프트: 해설집 + 사용자가 쓴 **해설 노트(`userNotes`) 전문**
2. 그 스팟 대화의 **이전 내용 전체** (사용자 질문, AI 답변, 생각 블록 포함)
3. 첫 질문에 붙는 스팟 정보(`facts`). 기록 화면에서 연 대화면 `Attempt.detail`도 들어간다
4. 모델, 해설 깊이

- **서버 키 방식(기본값)**: 이 요청 본문이 우리 Vercel 함수(`api/anthropic.ts`)를 지나 Anthropic(미국)으로 간다. 설정에 접속 비밀번호를 넣어 두었으면 그것도 헤더로 함께 간다. 중계는 저장하지 않지만 Vercel 함수 로그에 요청 기록(IP 등)이 남는다.
- **내 API 키 방식**: 기기에서 Anthropic으로 바로 간다.
- 사용자 id, 기기 id, 이메일은 보내지 않는다(지금은 계정이 없다).
- 즉 해설 노트와 대화 내용은 서버 저장 여부와 별개로 **지금도 코치를 쓸 때마다 국외로 전송된다.** 처리방침의 국외 이전 항목에 적는다(6장).
- 사용자가 자유 텍스트(질문, 노트)에 직접 쓴 개인정보는 막을 수 없다. 입력창에 "이름·연락처 같은 개인정보는 쓰지 마세요"라고 안내한다.

### 5.2 개인정보 수준별 정리

- **저장함, 높음**: 이메일 주소, 소셜 로그인 공급자가 준 이름·닉네임·프로필 사진. Supabase가 기본으로 저장하므로 동의항목을 줄이고 남는 것은 지운다. 지우기 전까지는 수집 항목으로 본다.
- **저장함, 중간**: 로그인 공급자 id, 결제 기록 참조, 로그와 세션의 IP, 해설 노트(사용자가 서버 저장을 켰을 때).
- **저장함, 낮음**: 공부 기록, 설정, 사용량, 권한, 동의 기록, 사용자 레이팅.
- **보내지만 저장하지 않음**: AI 대화 내용(질문·답변 전체), 해설 노트(AI 요청 때마다), 접속 비밀번호.
- **보내지 않음**: 생년월일, 전화번호, 카드 정보.

## 6. 처리를 맡기는 곳(위탁)과 국외 이전

Supabase를 서울 리전에 두더라도 Anthropic과 Vercel 때문에 국외 이전은 생긴다. 그래서 "해외 리전이면 적는다"가 아니라 **항상 적는다.** 아래 표를 처리방침의 위탁(개인정보 보호법 제26조)과 국외 이전(제28조의8: 항목, 국가, 시기·방법, 받는 자와 연락처, 목적·보유기간, 거부 방법과 그 결과) 항목으로 옮긴다. 구체 문구는 법무 확인한다.

| 받는 곳 | 맡기는 일 | 넘어가는 항목 | 국가·리전 | 보관 |
|---|---|---|---|---|
| Supabase | 로그인, DB 저장 | A·B 전체, 이메일, 소셜 로그인 정보, 세션·IP | 리전 결정 후 기재 (서울을 골라도 회사는 미국) | 8장 규칙, 백업은 Supabase 보관 기간 |
| Vercel | 앱·API 호스팅, 운영 로그 | IP, 요청 경로, AI 대화 중계 | 함수 리전 (지금 `vercel.json`에 지정이 없어 Vercel 기본 리전인 미국 동부에서 돈다. 서울 `icn1`로 바꿀 수 있다). 로그 저장 위치는 확인 필요 | 요금제별 로그 보관 기간 |
| Anthropic | AI 코치 답변 생성 | 질문, 이전 대화, 해설 노트, 스팟 정보 (사용자 id·이메일·IP 제외) | 미국 | Anthropic 정책에 따름 |
| 이메일 발송 업체 (Supabase 기본 발송 또는 별도 업체) | 인증코드 메일 발송 | 이메일 주소 | 업체 결정 후 기재 | 업체 정책 |
| RevenueCat / 토스페이먼츠 / 포트원 | 결제·구독 처리 | 사용자 id(고객 키), 결제 정보 | 업체별 기재 | 법정 보존 기간 |

## 7. 익명 사용자가 서버에 남기는 것

- **퀴즈·차트·계산기·기록 화면만 쓰는 사용자**: 서버 계정을 만들지 않는다. 서버에 남는 것은 앱 파일 요청의 운영 로그뿐이다. AI 코치를 쓰면 5.1의 전송과 중계 로그가 생긴다.
- **Supabase 익명 계정을 만드는 시점**: 사용자가 만 19세 이상 확인을 마치고 실시간 AI 대화를 처음 쓸 때, 또는 가입할 때. 설치 직후에는 만들지 않는다.
- 익명 계정에 남는 것: Supabase 익명 사용자 행, 세션, `profiles.age_verified_at`, `usage_counters`.
- 가입으로 이어지지 않은 익명 계정은 마지막 사용 후 90일이 지나면 함께 지운다(익명 사용자는 탈퇴 절차가 없으므로 자동 파기 규칙이 필요하다).
- **만 14세 미만**: 아동의 개인정보는 받지 않는다. 가입과 AI 대화는 만 19세 확인 뒤에만 열리므로 법정대리인 동의 절차는 두지 않는다(법무 확인).

## 8. 탈퇴하고 지울 때

1. 탈퇴 요청 즉시 로그인을 막는다(`deleted_at`).
2. 30일 유예: "실수로 한 탈퇴의 철회와 오남용 방지"를 목적으로 처리방침에 적는다. 이 기간에는 로그인, 동기화, 집계 등 어떤 용도로도 쓰지 않는다. 개인정보 보호법은 불필요해진 개인정보를 지체 없이 파기하도록 하므로, 30일 유예가 허용되는지와 그 기간은 법무 확인한다.
3. 유예가 끝나면 A·B를 파기한다. 예외는 셋이다.
   - 결제 기록: 법정 보존 기간 동안 사용자와 분리해 보관한 뒤 파기한다.
   - 약관·처리방침 동의 기록: 분쟁 대비 기간(법무 확인 후 확정) 동안 분리 보관한다.
   - 운영 로그: 탈퇴와 관계없이 정한 보관 기간이 지나면 지워진다.
4. 파기한 데이터도 Supabase 백업에는 백업 보관 기간(요금제별)만큼 남는다. 그 기간과 "백업은 보관 기간이 지나면 자동으로 지워진다"는 점을 처리방침에 적는다.
5. 기기 안의 데이터(B의 원본, C 전체)는 그대로 남는다. 앱 안에 "이 기기의 기록도 지우기"를 따로 둔다.
6. E(익명 집계)는 이미 사용자와 연결이 끊긴 숫자라 지우지 않는다. 처리방침에 이렇게 적는다. 사용자 레이팅은 A라서 함께 지운다.

## 10. 나중에 비용을 정할 때 볼 것 (아직 결정하지 않음)

- **용량의 대부분은 퀴즈 기록이다.** 실측으로 한 건이 기기에서 약 0.5KB다(16건 ≈ 8.4KB). 서버에서는 인덱스와 jsonb를 합쳐 대략 1KB로 본다.
- 대략적인 크기: 활성 사용자 1,000명 × 하루 20문제 = 하루 2만 건, **1년에 약 730만 건, 약 7GB**. A는 이에 비하면 무시할 수준이다.
- 조절할 수 있는 것과 그 대가:
  - 서버에는 `detail`(스팟 설명 텍스트)을 빼고 올리기. 한 건 크기가 크게 준다. **대신 다른 기기에서는 그 문제의 카드·보드·스택을 되살릴 수 없다.** `spot`은 무작위 부분을 뺀 묶음 키(`odds:<주제>`, `play:<구간>:<스트리트>`)라서, 다시 만들 수 있는 것은 프리플랍 퀴즈(`preflop:<시나리오>:<핸드>`, 같은 차트 세트 버전일 때)뿐이다. 레인지 암기는 핸드만 남고 블라인드 레벨·칩 수는 사라진다.
  - `detail`은 오답만 올리거나, 90일이 지나면 지우기.
  - 오래된 기록을 월별 요약으로 압축하기.
- 로그를 3개월 보관해야 한다면(A 운영 로그) 로그 저장소 비용이 따로 생긴다.
- AI 비용은 3단계(AI 해설 한도)에서 따로 정한다. C의 "대화 내역 미저장"과 D의 "미리 만든 해설"이 가장 큰 절감 장치다.

## 11. server-design.md와 달라지는 점

| server-design.md | 바뀌는 점 |
|---|---|
| 4장 "Postgres, Neon 추천", "인증은 직접" | Supabase(Postgres + Auth)로 바꾼다. `SqlClient` 방식은 그대로 쓴다 |
| 5.1·5.2 익명 기기 계정, HMAC 토큰 | Supabase 익명 로그인과 Supabase 세션 토큰(JWT)으로 바꾼다. `server/auth.ts`의 발급 부분은 필요 없어지고, 검증 부분만 Supabase 토큰 검증으로 바꾼다. 익명 계정을 만드는 시점은 7장을 따른다(설치 직후가 아님) |
| 5.3 기기 비밀값 | Supabase 세션이 기기에 보관되므로 대신할 수 있다. 연결할 때 다시 판단한다 |
| 5.4 Apple/Google/이메일 연결과 병합 | 카카오가 추가된다. 익명 계정에 소셜 로그인을 붙이는 일(계정 승격)은 Supabase가 지원한다. 이미 있는 계정과 합치는 병합은 여전히 우리가 처리한다 |
| 8장 "익명 계정도 결제할 수 있다" | 익명 사용자는 결제할 수 없다(9장). 결제 전에 가입을 요구한다 |
| `001_init.sql` | `users`는 `profiles(id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE, created_at, deleted_at, ...)`로 바꾸고, `auth_identities`는 Supabase가 관리하므로 지운다. `attempts`, `devices`, `usage_counters`, `entitlements`는 열 구성은 그대로 두되 `user_id text REFERENCES users(id)`를 `user_id uuid REFERENCES profiles(id) ON DELETE CASCADE`로 바꾼다(지금 사용자 id는 26자 텍스트, Supabase는 uuid). 8장 파기 규칙이 이 연쇄 삭제에 기대므로 반드시 함께 바꾼다 |
| `server/store.postgres.ts`, `server/router.ts` | `users` 조회·잠금(`FOR UPDATE`), `getOrCreateUserForDevice`, `/auth/anonymous`를 `profiles` 기준으로 고치거나 없앤다. 코드를 그대로 재사용할 수는 없다 |

이 변경은 서버를 실제로 연결할 때 코드에 반영한다. 지금 코드는 테스트로만 돌고 배포해도 503이라 급하지 않다.
