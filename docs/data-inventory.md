# PubAZ 데이터 구분: 회원 이후 서버가 관리할 것 / 아닌 것

> 상태: **설계 1단계 (회원 시스템)**, 2026-11-05. 비용(DB 용량, 요금)은 아직 정하지 않았다. 8장에 나중에 비용을 정할 때 볼 것만 모아 둔다.
> 서버 전체 구조는 [`server-design.md`](server-design.md)에 있다. 이 문서의 결정이 그 문서와 다르면 이 문서가 우선한다(9장).

## 1. 1단계 결정 기록

| 항목 | 결정 | 메모 |
|---|---|---|
| 가입 시점 | **익명으로 시작** | 설치하면 바로 쓴다. 기록 백업, 기기 이동, Pro 결제, AI 추가 횟수가 필요할 때 가입을 권한다 |
| 로그인 수단 | **카카오, 애플, 구글, 이메일 인증코드** | 이메일은 비밀번호 없이 일회용 코드로 한다 |
| 인증 방식 | **관리형 Supabase** (Auth + Postgres) | 익명 로그인과 위 네 가지 로그인을 Supabase가 처리한다. 우리가 만든 HMAC 토큰은 Supabase 토큰 검증으로 바뀐다(9장) |
| 나이 | **만 19세 이상 (잠정)** | 아래 참고 |

**나이 정책 메모.** 비교 대상인 GTO Poker Trainer(Peka Software)는 앱 등급이 4+이고 앱 사용에는 연령 제한이 없다. 18세 확인은 AI에 직접 질문하는 "Ask Nash"를 처음 쓸 때만 받는다. PubAZ는 익명 시작을 골랐기 때문에, 실제로 나이를 확인하는 순간은 **가입할 때와 AI 대화를 처음 쓸 때**뿐이다. 즉 결과적으로 "앱은 누구나, 가입·AI는 만 19세 이상"이 되어 Peka 방식과 거의 같다. 앱 사용 자체를 19세로 막을지는 스토어 등급을 정할 때 다시 본다.

## 2. 분류 기준

모든 데이터를 아래 다섯 칸 중 하나에 넣는다. "관리한다"는 서버가 저장하고, 백업하고, 탈퇴 시 지우고, 개인정보처리방침에 적는다는 뜻이다.

| 분류 | 원본 | 서버가 하는 일 | 관리 부담 |
|---|---|---|---|
| **A. 회원 데이터** | 서버 | 저장, 권한 판단, 탈퇴 시 파기 | 있음 (개인정보 포함) |
| **B. 동기화 데이터** | 기기 | 로그인한 사용자의 복사본 보관, 다른 기기로 전달 | 있음 (용량이 가장 큼) |
| **C. 기기 전용 데이터** | 기기 | 받지도 저장하지도 않음 | 없음 |
| **D. 배포 콘텐츠** | 우리(운영자) | 누구에게나 같은 파일을 내려줌 | 버전 관리만 (개인정보 없음) |
| **E. 익명 집계** | 서버 | 사용자 id 없이 숫자만 보관 | 작음 (나중 단계) |

판단 순서:
1. 우리가 만든, 누구에게나 같은 것이면 **D**다.
2. 비밀값이거나 우리 서버에 있으면 안 되는 것(API 키, 기기 비밀값)이면 **C**다.
3. 권한, 돈, 한도, 법적 기록처럼 서버가 정답을 가져야 하는 것이면 **A**다. 기기 값은 믿지 않는다.
4. 사용자의 공부 기록이고 기기를 바꿔도 따라와야 하는 것이면 **B**다.
5. 나머지(화면 상태, 대화 내역, 다시 만들 수 있는 것)는 **C**다.

## 3. 전체 표

### A. 회원 데이터 (서버가 원본)

| 데이터 | 지금 | 회원 이후 위치 | 개인정보 | 탈퇴 시 | 보존 |
|---|---|---|---|---|---|
| 사용자 id, 가입일, 탈퇴 상태 | 없음 (설계: `users`) | Supabase `auth.users` + 우리 `profiles` | 낮음 | 탈퇴 요청 즉시 로그인 불가, 30일 뒤 파기 | 계정 유지 동안 |
| 로그인 연결 (카카오·애플·구글·이메일) | 없음 (설계: `auth_identities`) | Supabase `auth.identities` | 중간 (공급자 id) | 파기 | 계정 유지 동안 |
| 이메일 주소 | 없음 | Supabase `auth.users.email` | **높음** | 파기 | 계정 유지 동안. 소셜 로그인이 이메일을 주더라도 꼭 필요할 때만 저장한다 |
| 연령 확인 기록 | 없음 | `profiles.age_verified_at`, `age_method` | 낮음 | 파기 | 계정 유지 동안. **생년월일은 저장하지 않는다.** "만 19세 이상 확인됨"과 시각만 남긴다 |
| 약관·개인정보처리방침 동의 | 없음 | `consents(user_id, doc, version, agreed_at)` | 낮음 | 파기 (분쟁 대비 기간은 법무 확인) | 계정 유지 동안 |
| 마케팅 수신 동의 (선택) | 없음 | `consents` | 낮음 | 파기 | 철회 즉시 반영 |
| 요금제·권한 (Pro, 만료일) | 없음 (설계: `entitlements`) | `entitlements` | 낮음 | 파기 | 계정 유지 동안 |
| 결제 기록 참조 | 없음 | `payments(user_id, provider, external_id, amount, at)`. 카드 정보는 결제사가 보관하고 우리는 받지 않는다 | 중간 | **법정 보존 기간이 지난 뒤 파기** | 전자상거래법상 계약·결제 기록 5년 (법무 확인) |
| AI 사용량 카운터 | 없음 (설계: `usage_counters`) | `usage_counters` | 낮음 | 파기 | 최근 40일만 남기고 지운다 |
| 기기 목록 | `pubaz.device` (기기 안) | `devices(device_id, user_id, platform, last_seen_at)` | 낮음 | 파기 | 계정 유지 동안. 90일 안 쓴 기기는 정리 |
| 접속·오류 로그 | 없음 | Vercel/Supabase 로그 | 중간 (IP) | 보관 기간이 지나면 자동 삭제 | 3개월 (통신비밀보호법, 법무 확인) |

### B. 동기화 데이터 (기기가 원본, 로그인한 사용자만 서버에 복사본)

| 데이터 | 지금 위치 | 서버 | 개인정보 | 탈퇴 시 | 메모 |
|---|---|---|---|---|---|
| **퀴즈 기록 (`Attempt`)** | localStorage `pubaz.attempts.v1` | `attempts` (설계 완료, 코드 있음) | 낮음 (공부 기록) | 서버 복사본 파기, 기기 기록은 남음 | 용량의 대부분을 차지한다(8장). 추가만 하므로 충돌이 없다 |
| 이전 합계 (기록 기능 이전의 정답률·문제 수) | localStorage `mygto.stats` | `legacy_tallies(user_id, payload)` 한 번만 업로드 | 낮음 | 파기 | 이 업데이트 이전에 푼 문제는 합계밖에 없어서, 첫 동기화 때 기준값으로 한 번 올린다. 이후 합계·연속 정답은 기록에서 다시 계산할 수 있으므로 서버가 따로 관리하지 않는다 |
| 학습 설정: 차트 세트, AI 모델 선택, 해설 깊이 | localStorage `mygto.settings` (`chartSet`, `model`, `effort`) | `profiles.prefs` (작은 JSON) | 없음 | 파기 | 기기를 바꿔도 같은 환경이 되게. 마지막에 바꾼 값이 이긴다 |
| 나만의 해설 노트 | localStorage `mygto.settings.userNotes` | `profiles.notes` (**선택**: 사용자가 켜야 올림) | 중간 (자유 텍스트라 무엇이든 쓸 수 있다) | 파기 | AI 코치 시스템 프롬프트에 들어가는 글이다. 서버가 프롬프트를 소유하는 단계(server-design 7.3)에서는 서버가 이 글을 읽어야 하므로 그때 기본값을 다시 정한다 |

### C. 기기 전용 데이터 (서버로 보내지 않음)

| 데이터 | 지금 위치 | 이유 |
|---|---|---|
| 내 Claude API 키 | `mygto.settings.apiKey` | 비밀값이다. 서비스 단계에서는 이 방식 자체를 "개발자 모드"로 숨긴다 |
| 접속 비밀번호 | `mygto.settings.passcode` | 지금 Vercel 중계용 임시 수단이다. 회원 시스템이 생기면 없앤다 (`keyMode`도 함께) |
| AI 코치 대화 내역 | localStorage `mygto.coach` (스팟별 최근 40개, AI 응답 원문 포함) | 개인정보가 섞이기 쉽고 데이터 중 가장 크다. 서버는 AI에 **중계만 하고 저장하지 않는다** (Peka도 같은 방식). 기기 간 이동이 꼭 필요해지면 나중에 사용자가 켜는 옵션으로만 연다 |
| 기기 비밀값 (예정) | 아직 없음 (server-design 5.3) | 내보내기 파일에도 넣지 않는다. Supabase 익명 로그인을 쓰면 Supabase의 세션 토큰이 이 역할을 대신하므로 필요 없어질 수 있다(9장) |
| 로그인 세션 토큰 (예정) | Supabase SDK가 기기에 보관 | 서버가 발급하지만 저장소는 기기다. 서버는 서명만 검증한다 |
| 화면 상태 (필터, 고른 탭, 진행 중인 핸드) | React 메모리 | 다시 만들 수 있다 |
| 기록 내보내기 파일 | 사용자가 받은 JSON | 사용자 소유다. 기기 id가 들어 있으므로 공유하지 말라고 안내한다 |

### D. 배포 콘텐츠 (누구에게나 같음, 개인정보 없음)

| 데이터 | 지금 | 회원 이후 |
|---|---|---|
| 프리플랍 차트 세트 | 앱 코드 안 (`src/data/sets/*.ts`) | 앱 코드 또는 콘텐츠 팩. 버전을 붙여 `Attempt.spot`과 함께 "어느 차트 기준 채점인지" 남길 수 있게 한다 |
| 솔버 콘텐츠 팩 (포스트플랍) | 없음 | 정적 파일 + 매니페스트 (server-design 9장) |
| 오늘의 문제 문제 풀 | 없음 | 정적 파일 (server-design 10장) |
| 미리 만든 AI 해설 | 없음 | 정적 파일. 같은 스팟이면 모든 사용자에게 같은 해설을 주므로 사용자별 AI 비용이 들지 않는다 |
| AI 코치 해설집 | 앱 코드 안 (`src/features/coach/knowledge.md`) | 서버가 프롬프트를 소유하는 단계에서 서버로 옮긴다 |

### E. 익명 집계 (나중 단계)

| 데이터 | 만드는 곳 | 원칙 |
|---|---|---|
| 문제별 난이도·정답률 (문제 레이팅) | 서버가 `attempts`에서 집계 | 사용자 id 없이 숫자만 저장한다 |
| 펍 필드 통계 (사람들이 실제로 어떻게 치나) | 사용자가 켠 핸드 기록에서 집계 | 동의한 사용자만. 집계 인원이 적으면(예: 10명 미만) 공개하지 않는다. 실존 인물 닉네임 단위의 기록은 만들지 않는다 |

## 4. 기기 저장소 정리 (localStorage 키별)

| 키 | 내용 | 분류 |
|---|---|---|
| `pubaz.attempts.v1` | 퀴즈 기록 | B |
| `pubaz.device` | 기기 id | A의 "기기 목록"에 쓰인다. 값 자체는 기기에 둔다 |
| `mygto.stats` | 정답률 합계, 연속 정답 | B (이전 합계만 한 번 업로드, 나머지는 기록에서 재계산) |
| `mygto.settings` | 키 방식, 비밀번호, API 키, 모델, 해설 깊이, 해설 노트, 차트 세트 | **필드마다 다르다**: `apiKey`·`passcode`·`keyMode` = C, `model`·`effort`·`chartSet` = B, `userNotes` = B(선택) |
| `mygto.coach` | AI 대화 내역 | C |

회원 시스템을 붙일 때 `mygto.settings`를 둘로 나눈다. 비밀값(C)은 기기 전용 키로, 학습 설정(B)은 동기화용 키로 옮긴다. 한 키에 섞여 있으면 실수로 비밀값까지 올릴 수 있기 때문이다.

## 5. 서버로 가는 데이터의 개인정보 수준

- **높음**: 이메일 주소 하나뿐이다. 소셜 로그인 공급자가 주는 이름·프로필 사진은 받지 않거나 저장하지 않는다.
- **중간**: 로그인 공급자 id, 결제 기록 참조, 접속 로그의 IP, 해설 노트(자유 텍스트).
- **낮음**: 공부 기록, 설정, 사용량, 권한.
- **보내지 않음**: 생년월일, 전화번호, 실명, 카드 정보, AI 대화 내용.

AI 코치에 보내는 내용(스팟 정보와 질문)은 서버를 지나가지만 저장하지 않는다. Anthropic에도 사용자 id와 이메일을 보내지 않는다(server-design 7.3).

## 6. 탈퇴할 때

1. 탈퇴 요청 즉시 로그인을 막는다(`deleted_at`).
2. 30일 뒤 A·B를 전부 파기한다. 단 결제 기록은 법정 보존 기간 동안 사용자와 분리해 따로 보관한 뒤 파기한다.
3. 기기 안의 데이터(B의 원본, C 전체)는 그대로 남는다. 앱 안에 "이 기기의 기록도 지우기"를 따로 둔다.
4. E(익명 집계)는 이미 사용자와 연결이 끊긴 숫자라 지우지 않는다. 개인정보처리방침에 이렇게 적는다.

## 7. 로그인 전후로 바뀌는 것

| | 익명 (가입 전) | 로그인 후 |
|---|---|---|
| 퀴즈, 차트, 계산기, 기록 화면 | 전부 됨 | 전부 됨 |
| 기록 보관 | 이 기기에만 | 기기 + 서버 복사본 |
| 다른 기기에서 기록 보기 | 내보내기/가져오기로만 | 자동 |
| AI 해설 | 익명 한도 (2단계에서 정함) | 회원 한도. Pro면 더 많이 |
| Pro 결제 | 안 됨 (기기를 잃으면 결제도 잃으므로) | 됨 |

## 8. 나중에 비용을 정할 때 볼 것 (아직 결정하지 않음)

- **용량의 대부분은 퀴즈 기록이다.** 실측으로 한 건이 기기에서 약 0.5KB다(16건 ≈ 8.4KB). 서버에서는 인덱스와 jsonb를 합쳐 대략 1KB로 본다.
- 대략적인 크기: 활성 사용자 1,000명 × 하루 20문제 = 하루 2만 건, **1년에 약 730만 건, 약 7GB**. A는 이에 비하면 무시할 수준이다.
- 조절할 수 있는 것:
  - 서버에는 `detail`(스팟 설명 텍스트)을 빼고 올리기. 한 건 크기가 크게 준다. 다른 기기에서 해설을 다시 볼 때는 `spot`으로 다시 만든다.
  - `detail`은 오답만 올리거나, 90일이 지나면 지우기.
  - 오래된 기록을 월별 요약으로 압축하기.
- AI 비용은 2단계(AI 해설 한도)에서 따로 정한다. C에 둔 "대화 내역 미저장"과 D의 "미리 만든 해설"이 가장 큰 절감 장치다.

|---|---|
| 4장 "Postgres, Neon 추천", "인증은 직접" | Supabase(Postgres + Auth)로 바꾼다. SQL 스키마와 `SqlClient` 방식은 그대로 쓴다 |
| 5.1·5.2 익명 기기 계정, HMAC 토큰 | Supabase 익명 로그인과 Supabase 세션 토큰(JWT)으로 바꾼다. `server/auth.ts`의 발급 부분은 필요 없어지고, 검증 부분만 Supabase 토큰 검증으로 바꾼다 |
| 5.3 기기 비밀값 | Supabase 세션이 기기에 보관되므로 대신할 수 있다. 연결할 때 다시 판단한다 |
| 5.4 Apple/Google/이메일 연결과 병합 | 카카오가 추가된다. 익명 계정에 소셜 로그인을 붙이는 일(계정 승격)은 Supabase가 지원한다. 이미 있는 계정과 합치는 병합은 여전히 우리가 처리한다 |
| `001_init.sql`의 `users`, `auth_identities` | `users`는 `profiles`(id = Supabase 사용자 id)로, `auth_identities`는 Supabase가 관리하므로 지운다. `attempts`, `devices`, `usage_counters`, `entitlements`는 그대로 둔다 |

이 변경은 서버를 실제로 연결할 때 코드에 반영한다. 지금 코드는 테스트로만 돌고 배포해도 503이라 급하지 않다.
